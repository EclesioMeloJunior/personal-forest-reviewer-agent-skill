# Shell, Docker, CI

- Bash is hard enough; do not make it clever. `${X:?}` → `if [ -z "$X" ]`. Short flags → long flags unless universally known: "unless a flag is obvious, e.g., `rm -rf`, I recommend using full versions of the params, e.g., `--silent` instead of `-s`." A growing bash harness becomes Rust: "this bash script is horrible. 😆 We need to convert it to proper Rust code to make it maintainable."
- Inline shell in compose/YAML longer than a few lines → a dedicated script so shellcheck sees it, with comments on every regex. "This logic is pretty convoluted. What are you trying to achieve?"
- "nit: can we avoid those nasty escapes?" Use a heredoc or `jq`. Parse structured output (JSON), never human-readable dumps.
- Magic numbers get a one-line origin: "13 is a magic number; I know where it comes from but it'd help the readers to know what it is."
- A workflow with two inputs where one required input would do: "then you could mark it as required and avoid conditionals." Copied-over comments that no longer hold: "This comment is incorrect. Leftover from copypasta?" Convoluted workflow `if:` conditions get a comment "for those of us that don't have PhD in De Morghan laws". `always()` in a condition: "what's the point of `always()`?"
- Runners: "The house rule is to use the `arm` version unless not possible (cheaper & faster)."
- `apt-get` in CI is wrapped with `nick-fields/retry` (see `rust-lint.yml`): "Ubuntu apt repos are known to fail." Installing tools on every run is the wrong design anyway: bake an image on top of the existing one. Pin tool versions (`taplo-cli`, `cargo-deny`). Path-filter lint workflows to the directories they lint. Parallelise independent `mise` tasks.
- Images: `latest` is never the answer for something that should be reproducible (`docs/docs/users/knowledge_base/docker_tips.md#tags`); a pinned date tag is never the answer for a nightly check; and think about publish races: "Imagine you merged something at 1 PM. The docker image has not yet been published. What happens?" Platform games (`platform: linux/amd64`) → publish a multi-arch image instead. "PR branches must not overwrite the `edge` tag."
- Everything dockerized, nothing on the host: init containers over host scripts, no `curl`/`jq` host dependencies, no GNU-vs-BSD `date` tricks. No exposed ports unless something outside the compose network needs them: "I often have Forest running on my own machine; I don't want to turn it off because of some needless port conflicts."
- Production-like tests use the real `forest` daemon, not `forest-tool api serve`. Health checks come from `docs/docs/users/guides/monitoring/health_checks.md`, not `forest-cli chain head`.
- Timeouts and retries must be proportionate: "So... potentially 20h for the probe to fail?" "After 2h the patient is likely dead." "why would it take so long? how long does this take normally?" "tons of magical timeouts, each with different value. Why?"
- Big downloads: `aria2c -x5`, not `curl`.
- Generated code is marked generated (`.gitattributes`, see `src/rpc/snapshots/.gitattributes`) or, better, not committed: "is this not generated? So, could we not add it to the source?"
- Borrowed artifacts (a `.proto`, a constant, a Lotus algorithm) carry a permalink to where they came from.
- New tests run in CI or the PR says why not: "Any reason why those tests are not invoked in CI?" Long suites go behind a label, the `Release` label, or nightly, wired up in a separate PR first. CI flakiness is understood, not reverted: "we need to understand why this is happening in the first place ... Could you please create a tracking issue?" "If it works in one workflow and doesn't in another we should understand it."
- `overflow-checks = true` on the profiles CI builds, since "we don't ship `quick` binaries anywhere".
- Spellcheck dictionary holds real words only; identifiers go in backticks at the source: "The dictionary should not contain entries such as class or module names ... F1..F28 - it's not an entry for the dictionary."
