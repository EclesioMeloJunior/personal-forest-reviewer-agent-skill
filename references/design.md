# Design pass

Read the whole change once before commenting on a line. The questions maintainers ask first:

- Is this needed at all? "Is this code really needed? There are exactly 4 invokers of the remote dispatch (us) and if the image pull fails we'll get exactly an error saying that the image is garbage." "Let's not write more code than we have to."
- Why now? "Why do we need this config now and didn't need it before?" "Hm, why do we need this? Why was it not needed before?"
- Root cause before fix. "I don't quite understand. Could you please explain what was the issue and how this change fixes it?" "But why is that?" "I don't think it's confirmed that was the culprit." Moving a problem is not fixing it: "it just pushes the overflow to another place."
- Is there something in the tree already? "Do we have some crates in the tree that'd already do it for us?" Point at the existing thing (`api_compare` compose, health checks docs, `rstest` usage elsewhere, `optimize_disk_space_gh_worker.sh`). "There's a dedicated method for this."
- Is it in the right place? Ask this for every new function, type, and trait method, before anything else on that line. A feature landing in `*util`, `*_util`, `helpers`, or a `mod.rs`: "`*util` type of modules are supposed to be small utilities, not full features. It should likely be a separate file." "It's usually nice to have the `mod.rs` only resolve around what to export from a crate." A method bolted onto a trait whose purpose it does not share: "It's kind of weird this is a part of this trait, but it's outside of the scope of this PR to redesign it." (say it even when it is out of scope). A free function taking the struct is a method: "this is essentially a method on the keystore that requires the keystore". `rpc/*` holds only RPC handling; chain logic lives elsewhere. Shims mask actor versions completely: "Let's not use specific versions of actors/fvm directly. Ideally, only shims would would deal with those." A method that was already bloated and grew again: "This method is already bloated and way too big. This should be refactored." Refactors of user-critical code start move-only: "A good first step in doing some refactoring would be just moving things around (without ANY logic changes)".
- Panic policy, three-way. Daemon code never panics on input: "That's a bit scary - we shouldn't crash the entire Forest on a bad reader." "Mind that messages are user-supplied so they can and will be malicious." "I don't feel comfortable with panicking on user-provided input." A path reachable only through an implementation bug is `unreachable!`, not `bail!`. CLI tools propagate errors: "I understand those are short-lived commands, but panics are really a bad user experience. Let's propagate errors with helpful messages, by the book." Every `unwrap`/`expect`: "why `unwrap`? Is it infallible?" "If it's infallible, then why does the function even returns a `Result`?" A "can't happen" branch logs instead: "Perhaps now it's handled but later one someone will change some code and Forest will start crashing out of nowhere."
- Silent failure is a bug. Matching integers with `_ => {}`: "we shouldn't silently fail." Use an enum: "whenever a new variant is introduced, the entire build fails for places where it's matched non-exhaustively. The alternative is finding the issues in runtime, which is not ideal and brings us closer to Python land (a bad place)." No wildcard arm on an enum that will grow: "Say we introduce `ApiPaths::V3`; this `match` wouldn't get caught by the compiler." Never swallow an error: "Can we not swallow the error from `from_filecoin_address`? It might contain some useful information." A command that hits a problem exits non-zero: "it silently failed with return code zero, thus it flew under the radar." A swallowed error gets "what are the implications of lost data?"
- Strong typing. "In the land of Rust, let's use strong typing and not strings when possible." Strings in signatures become `Url`, `PathBuf`, `Cid`, enums: "`Url`?" "Can this be strongly typed?" Raw ints become aliases: "can we please not use `i64` for when `ChainEpoch` would be more expressive?" Errors are types, not strings: "Can we have `EthTrace` errors as proper errors, e.g., via thiserror? Less allocation overhead, cheaper operations and something actually strongly typed." Mutually exclusive bool CLI flags become one enum arg: "If we add another one, we'd just need add a value to the enum (and not handle cases like `--v2 --v3`)." Flag dependencies are encoded in clap, not docs.
- Is it brittle? A condition that happens to hold today is not a design. "The exactly same bug would be necromanced if tomorrow someone introduces `lightspeednet`." Prefer forcing the decision on the caller (constructor parameter, enum) over inferring it from a property that coincidentally correlates. Forest never depends on the CWD or `/tmp`: "Forest behavior mustn't depend on the CWD - I might be running Forest from `/tmp` or even from some HDD. It's also not nice to spam leftovers in case something fails." Tests never self-skip on sniffed environment: "I don't trust the system that can skip things on its own."
- Unbounded anything on a public RPC node is an attack vector. "This map grows unbounded. On a long-running public RPC node this could be a vector of attack." Every cache states its expected max size and per-entry cost, capped by how hot the path is: "what's the expected maximum size of this cache?" "IMO 83 MiB is quite a bit ... Let's limit it to like 8 to survive a burst but that's about it." "What's the memory increase if cache is full?" "What's the expected memory footprint of a maxed-out eth block cache?" "Shouldn't we still put some bounds on it, like at most 4 GiB?" Recursion too: "does it make sense to enforce some limit on recursive calls here? We don't want to stack overflow."
- Concurrency. TOCTOU between check and act ("That's a TOCTOU!"), lock scope ("You put a write lock during GC - during this period all read operations are blocked, no?"), memory ordering ("Do you think `Ordering::Relaxed` is enough here?"), blocking in async ("You're still using sync sleep `std::thread::sleep`, whereas the _correct_ way is to use `tokio::time::sleep` so that the task can yield"), sleep-based synchronisation ("It's a bit shaky assumption; can we make it more resilient?"), nonce races in wallet tests.
- Does complexity pay for itself? "Is the performance gain relevant enough to make up for a complex logic? If we'd reuse what we already have ... what'd be the total ingestion time difference?" No number, no complexity. Manual plumbing of derived values loses to memoization: "It introduces a bit of complexity and manual handling to avoid redundancy. IMO it should be done via memoization, reducing any mental overhead." Parsing is fast and strict, no tolerance paid by every caller: "if a user puts tabs or whitespace in their input, well, they deserve errors." "I'd rather we are fast and strict."
- Performance claims need numbers even when the win looks obvious: "Is this faster than the previous implementation? Do you have a benchmark? I mean, it looks like it should be faster but I'd love some numbers." "How is this constant time?" Mainnet, repeated: "Let's have at least five runs before the change and five runs after, optimally from exactly the same tipset." "I'd love a mainnet export timings (let's say, 3 on each branch) because calibnet often doesn't surface any issues." "What's the memory footprint reduction?" Hot paths get a benchmark; caches must have minimal overhead on every push.
- Is this change consensus-affecting? Then ask for the Lotus source: "Given it's a consensus-affecting change, can we have a source to Lotus code with this logic?" Logic with no Lotus equivalent is suspect: "I wonder if it's even needed. There's no Lotus equivalent for this." Check network-version branches against mainnet, not just calibnet: "Would calling this with some old tipset on mainnet, pre-NV14, produce the same result in both Forest & Lotus?" For every changed RPC response structure: "please provide a link to the reference implementation". New RPC surface or spec text is agreed with FilOz/FIPs: "Is it agreed with FilOz that we add this RPC method?"
- Null rounds are an edge case for every height-indexed structure: "So what happens if there are more than 5 null epochs in row? It's possible, no? Especially on calibnet or a devnet." "What's the mapping in case of null tipsets?" Same for timing: "What if we're at the epoch boundary, e.g., 29s and Forest's latest is X and Lotus's is X+1?" "what if a bad fork arrives right after?"
- Breaking changes. Removing a flag, bounding an exposed method, renaming a metric or a file extension, flipping a default: "That's a breaking change, no?" Prefer a default over removal: "We can avoid a breaking change by making the `--recompute` default to `true`." Name the escape hatch: "Let's mention the env variable that allows bringing back whatever behavior the user might have depended on." When a flag's semantics change, check every script that uses it: "No existing scripts need to be updated?" "Do we need all 200 in practice?"
- Special cases that should not exist: "I don't exactly understand why you'd handle 404 in special way. If the metadata can't be downloaded for any reason, then it should just fail, regardless if it's `not found` or `i'm a teapot`." Ignore-lists are scoped: "It's not great to globally ignore fields with a given name. The ignores should be scoped to given methods." Parity failures are fixed, not suppressed: "The goal here is not to suppress the errors coming from strict JSON checks, but to provide a meaningful fix." "We should serialize correctly but allow legacy (Lotus) deserialization."
- Coupling that breaks the contract of an existing mechanism (e.g. RPC snapshots must stay self-contained; hardcoding fixtures in a random util that another test relies on makes them stale the moment the snapshot changes).
- Dependencies. A new crate needs a one-line reason: "Can you please summarise why it is needed?" Nothing unused in the tree: "I wouldn't like fjall to be in Forest's dependency tree if we don't use it." Feature flags are a last resort: "they make CI kind of annoying - you compile one thing for a release, then another for tests". "we cannot have git references in `Cargo.toml`, as it'd block any (potential emergency) releases". Actor crates come through the `fil-actor-states` re-export. Dev tooling is not shipped to users: "Ideally, this would be a part of `cargo bench` and not exposed to users at all." "I don't think we should enable experimental features unless proven to be working fine and give benefit." "until integrated, it's wasteful." Compile time matters: "it slows down the local compilation so unless a viable alternative profile is provided, we shouldn't remove it."
- Copy-pasta: "if you copy-pasted this code from somewhere, please update it there as well." Test-only code is `#[cfg(test)]`: "Test code shouldn't be mixed too much with production code." Follow-ups get a tracking issue now: "do we have a tracking issue? If not, let's create one to not forget about it." But a small fix lands here, not in a promised refactor: "It's a minimal change to do here, and, from experience, some refactors never land."
