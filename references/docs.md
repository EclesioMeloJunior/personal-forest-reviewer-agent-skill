# Changelog, docs, comments

- `CHANGELOG.md` follows the guide at the top of the file: `[#ISSUE](link): short description`, one line, user-facing only. CI, refactors, test infra, and internal mechanics do not go in: "Does this check affect the user?" "that's internal change, no need for changelog entry". Narrative is cut: "Let's skip the narrative." A fix goes under Fixed, not Changed: "It's a fix, not an arbitrary change." A non-transparent change without an entry: "Let's have a changelog entry. This is not a transparent change."
- What IS changelog material: fixes that manifested ("Did this bug manifest anywhere? ... If so, a changelog entry might be useful."), wrong metrics ("Worth a changelog entry, given metrics were incorrect."), perf wins and memory drops ("folks would like to know Forest potentially dropped its memory requirements by half", "That's amazing, worth putting in the changelog. ;)"), RPC changes even when unguaranteed ("We don't guarantee it, but it's still worth mentioning in case someone relied on it."). Breaking section for metric renames, file extension changes, default flips, flag removals: "This is a functional breaking change, hence a CHANGELOG entry is required." The entry names the affected methods: "What methods are affected? What was the gist of the issue? ... a single sentence would help." Current release train. Network upgrade entry lands when the epoch is scheduled.
- Release notes: short, no repeated celebration, no enumerated highlights ("There are also additional (breaking) changes and improvements; see below."). Pre-1.0 semver: "there are no breaking changes and we don't add support for anything major like a new network version. `0.36.1` is fine." versus "There were a couple of breaking changes; I suggest we bump to `0.32.0`". Mandatory-ness is stated per network: "Do we consider it mandatory for calibnet operators?" A breaking change to a dev tool still gets an entry: "I don't think anyone was actively using `forest-tool state compute` but in case they were, it'd be helpful to put an info."
- New env var → the table in `docs/docs/users/reference/env_variables.md`, not a paragraph below it; removed flags leave the docs. `AGENTS.md` is not bloated with things nobody needs: "after initial development, we never had to."
- Two-sided comment rule. Inline comments: short. "A good way to avoid docs drift is to not overdo the docs." "I'd trim those comments down, pretty long comments for such short code." "No need to put ballads of our epic battles with the borrow checker." "No need to explain what is `dnsaddr`." Test case names already explain the case. Rustdoc on `pub` items: generous. "Let's add some documentation for newly created methods and traits, especially when they are marked with `pub`." "I know it's in the FRC, but it'd be nice to have those fields documented regardless. Perhaps even some copy-pasta from the spec. ... AI tooling will also appreciate it." "Let's nicely document what this trait and its method are supposed to do (and why)." Module headers say what belongs in the file: "Kind of useful in preventing others putting whatever there." Private internals are explained in the code, not in method docs: "I'd rather not have method-level documentation, but rather explanations in the code itself." Existing comments survive refactors: "Let's keep the comments." And: "Let's not AI generate more documentation than there's actually code."
- Still wanted inline: a short "why" that will not be obvious "to other readers a year from now", docs on a method that can block, which fixture entry is needed by which test, a comment on a convoluted condition, "why is it five? Why not 10?"
- Docs live where the compiler sees them: module-level Rust docs over markdown guides ("anyone that modifies them get immediate feedback from the compiler, which reduces code/docs drift"); intra-doc links to real items and real file links "to have the CI break if the file is moved"; "Sanity check: does the method description still reflect the actual code?"
- Internals go to developer docs: "Users shouldn't care about the internals." Developer guides point at the workflow instead of narrating it: "It's developer guide, hand-holding not needed." The reverse holds too: "The developers guides are intended for Forest maintainers. This should be in user space." "Users don't need a guide on Anvil, they come here for Forest. ;)" Guides promote good security practice ("unencrypted keystores are not one of them"). Docs stay DRY, with permalinks ("Later we can change it to regular link (otherwise link check will fail)"). No Lotus links in public docs or OpenRPC ("they're an internal detail for our reference"); no Go-isms ("let's not use `nil` in Forest documentation"). One topic per document: "Network upgrade handling should be a separate document." Text survives the next upgrade: "Let's phrase in a way that won't require amendments when NV31 is there. :)" "no point in maintaining this comment with every network upgrade".
- Reports and benchmarks: neutral voice, hardware, versions, dates, sources. "Just showing the numbers and explaining them in boring, academic voice is fine." "Details of the hardware used must be added here to make this meaningful in any way. 10% CPU of what, 166 MHz single processor from 90s?" "Let's not tell people what to do. Rather, we should facilitate making informed decisions."
- Word precision via suggestion: "should" → "must", "non-zero" → "positive", "filename" → "file path", "_exempli gratia_ should be written `e.g.`". Typos get a suggestion block, nothing more.
