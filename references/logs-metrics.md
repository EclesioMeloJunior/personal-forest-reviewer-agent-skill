# Logs and metrics

- Logs are for operators. If an operator cannot act on it, it is `debug`. "Operators don't care about it." A `warn!` that can repeat under degraded conditions is a flood: "they'd get flooded with non-actionable warnings." A command that spams: "There's lots of spam/debug logs in the fetch command. Perhaps you need to setup the logger?"
- Level follows actionability and severity. For each swallowed or downgraded error: "Why would this fail? What's the severity of it? Can a node-operator do anything about it?" A bad config value is `error!`, not `warn!`. Advertised-and-not-importable is a failure, not a warning. "worth logging an error in case of fiasco on the daemon side?"
- Log and error text matches the user's mental model and tells them the fix: "If I'd be reading this as a user and see "validation starts in ~10 epochs" I'd expect it to start in 5 minutes." "why `~`? we know the exact value, no?" "Probably worth adding the error message that the state re-compute is disallowed ... let's save folks some hassle." CLI prints what it skipped. An opt-in env var gets no runtime warning: "if they made such decision consciously then the warning would just annoy them." User payloads in logs are truncated or `debug`; secrets never reach `info!` ("`Admin token saved to <PATH>` would preserve the functionality"); a broken invariant is more severe, not less: "If it's NOT subscribed then, from my understanding, something went terribly wrong, no?"
- Metrics are not free: "Prometheus metrics are scraped every X seconds, then persisted. We should keep only metrics useful to operators and ourselves." Durations and error counters for an internal fetch are debug information, not metrics. "We must not bloat the metrics." Monotonic values are counters: "It doesn't make sense for `hits` and `misses` to be `Gauge`; they're monotonically increasing." Names match contents (`eth_transaction` vs `eth_transaction_receipt`). Report the _actual_ state, with the expected one alongside "so consumers can set up an alarm if there's a mismatch". New metrics land in `docs/docs/users/reference/metrics.md`, with a section when two look alike; a Grafana panel is welcome.
- A counter sits exactly where the event happens, not somewhere that is "correct-ish ... only if you analyze the logic in the following lines."
- Duplicate metric registration is guarded at the highest level, not inside one cache.
- CLI UX may beat Lotus, RPC may not: "While we must maintain compatibility on the RPC layer, we're free to improve UX on the CLI level." Typed CLI args (`TokenAmount` so one can write `1milliFIL`, not attoFIL). "Does this increase startup time?" "does it make sense to run it in a stateless node?"
